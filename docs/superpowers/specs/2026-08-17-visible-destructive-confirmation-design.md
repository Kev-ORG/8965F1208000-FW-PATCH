# Visible Destructive Confirmation Design

## Goal

Make every destructive confirmation in `patch` and `restore` unambiguous in an
interactive SSH terminal. No command may silently block on an invisible long
`input()` prompt, and no writer may be armed unless the operator enters the
exact uppercase word `YES`.

## Scope

The behavior applies to every destructive writer invocation:

- target-sector patch writer;
- CRC-sector patch writer;
- every selected restore-sector writer, including both sectors of a two-sector
  restore.

Probe remains non-destructive and has no confirmation input. Transport timeouts
are not converted into confirmation prompts. FACI payloads, intent layouts,
erase/program ordering, sector order, binary artifacts, and automatic-retry
rules remain unchanged.

## CLI Contract

Before dispatching any `patch` or `restore` command, the CLI requires
`sys.stdin.isatty()` to be true. A non-interactive invocation fails before
preflight, payload loading, Panda connection, or artifact-state mutation with a
clear message that an interactive SSH terminal is required.

At each writer boundary the CLI prints and flushes:

```text
DESTRUCTIVE OPERATION
<complete transaction summary generated by the workflow>
Type YES to continue: 
```

Only the exact string `YES` is accepted. Lowercase text, leading/trailing
whitespace, an empty line, EOF, or any other value is rejected before the
workflow records `*_ARMED` and before the writer payload is triggered.

The CLI confirmation adapter returns the original transaction summary to the
existing workflow only after reading exact `YES`. This preserves the internal
exact-confirmation contract and its durable state ordering without teaching
the patch or restore workflow about terminal I/O.

## Failure Behavior

- Wrong input and EOF produce a clear expected CLI/workflow error.
- `Ctrl+C` remains a pre-arm cancellation when pressed at the confirmation
  prompt.
- A rejected confirmation records the existing pre-arm failure state and never
  invokes the destructive payload.
- The CLI never retries input and never retries a writer. The operator must
  start a new command intentionally.
- Planned power-cycle instructions are printed with forced flushing, state that
  the current command has exited, and retain the existing persist-exit-power-
  cycle-rerun behavior. They do not wait for Enter.

## Testing

Tests will prove that:

1. exact `YES` prints the complete transaction and authorizes the existing
   callback result;
2. every non-exact input and EOF fail without authorization;
3. non-TTY `patch` and `restore` fail before payload loading, preflight, or
   transport creation;
4. target patch, CRC patch, and all restore writer confirmations pass through
   the same CLI adapter;
5. `*_ARMED` is still persisted only after successful confirmation;
6. the complete existing suite remains green and payload/binary hashes remain
   unchanged.

## Safety Boundary

This is a host-side CLI visibility change only. It does not rebuild or modify
any V850 binary, change FACI stores, change candidate construction, change
restore order, or perform hardware/network operations during implementation.
